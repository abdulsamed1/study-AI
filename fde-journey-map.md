# FDE Journey Map — Deep Engineering Roadmap

**Purpose:** Build durable engineering capability for taking a real business problem from discovery to a reliable, evaluated, secure, deployed AI-enabled system. This is a long-form learning journey.

**Mission alignment:** FDE = problem discovery → choose the right solution (including non-AI) → build → evaluate → secure → deploy → integrate into work → measure impact → hand over. The target is demonstrable engineering judgment, not completion of a syllabus.

---

## 1. Rules for this journey

1. **Follow dependencies, not enthusiasm.** Each lesson lists its prerequisite lesson IDs. A lesson is ready only when its prerequisite's exit evidence exists.
2. **Teach one lesson unit at a time.** A unit normally takes 45–90 minutes of teaching and guided practice; larger implementation units may span several sessions. Estimated times are planning aids, not promises.
3. **Teaching mechanics live in `AGENTS.md`.** The lesson loop (teach → model → practice → review → retrieve later), evidence/synthesis separation, spacing, records, and honest phrasing of experience follow `AGENTS.md` §3, §5, §8, §11, and §13 — this map does not restate them.
4. **No progress by attendance.** Mark a lesson complete only when its proof artifact or practical performance meets the exit criteria.
5. **Respect established experience.** The user already has C++, OOP, and DSA experience. Do not teach beginner programming, object-oriented programming, or generic algorithm lessons. Use diagnostics to identify only the language, runtime, API, data, or AI-engineering gaps needed for the capstone.
6. **One evolving capstone.** Build a small, deterministic business workflow first; add persistence and integrations; introduce AI only when the use case justifies it; then evaluate, secure, deploy, pilot, and document it. Keep scope narrow.
7. **Source discipline.** `RESOURCES.md` remains the canonical project source register. Existing `S#` tags refer to it. The `F#` references below are official starting points checked on 2026-10-09; re-open the relevant page and record the exact section/version before teaching. Current API/model/security behavior must be verified at lesson time. A chapter tagged `[TOC]` was identified from a book's table of contents only and has not been read by the mentor; keep the tag until the exact passage is read in an available tool — ChatGPT Project, NotebookLM, or the local `books/` epub opened in OpenCode — and recorded in `RESOURCES.md` with book, edition, chapter or page, date, and tool. A read that covered only the supporting sections is tagged `(read: <sections>)`; a chapter read in full is tagged `(read)`.
8. **This is a dependency graph represented as a mostly linear path.** Some concepts can be revisited later. Do not force advanced internals when the mission does not need them.
9. **Stay on the FDE/AI-engineer track.** Out of scope: training or building foundation models, ML research, and math beyond the applied evaluation protocol in P14.3 (see `MISSION.md`). Teach models and providers as engineering constraints — guarantees, cost, latency, failure modes — never as model internals.
10. **Human-in-the-loop engineering.** The learner directs coding agents and stays accountable for the result; an agent's output is an input to review, never proof by itself. Before delegating, write the problem, requirements, constraints, acceptance criteria, and architecture decisions. After the agent changes the code, review the diff, its dependencies and side effects, and the tests it wrote; design at least one verification independently of the agent's own tests; observe the real behavior across API, application logic, database, and user-facing workflow; diagnose failures from logs, traces, measurements, and failure injection; then record accept, reject, or redirect with evidence (the agent review record in section 3). Passing tests are necessary, not sufficient (S40, S41). A lab proves a lab skill: label simulated data and pilots honestly, and phrase missing experience with the honesty rules in `AGENTS.md` §11. Projects in languages the capstone does not need (for example Rust) remain code-review contexts, not additional language tracks.

11. **Hand-writing versus review.** Hand-write first when the skill is the learning target: a new concept the learner has not yet demonstrated unaided, correctness-critical work (transactions, concurrency, authorization, idempotency), and debugging. Delegate repeated mechanics and work in skills the learner has already demonstrated unaided; the delegation brief, diff review, independent verification, and accept/reject/redirect decision stay exactly as in rule 10. When an agent is used to learn, use it to build comprehension as well as output — ask it for explanations and conceptual questions, not only for code (S44). Delegating never transfers accountability: the learner still explains, modifies, or fixes the result without the agent, and owns it in the evidence pack (P17.3–P17.4) (S43).

**Stages.** Five stages group the phases for orientation. A stage is not a gate and does not change unit order; the phase headers and the gate table remain the progression contract. The gate column names the gate that closes the stage, not a new stage-level gate.

| Stage | Phases | Learner-facing purpose | Gate at stage end |
|---|---|---|---|
| Foundations | 0–3 | Mission and problem brief; reproducible workbench; language/runtime bridge; service runtime | G1 after Phase 3 (G0 remains the Phase 0 gate) |
| Service engineering | 4–9 | HTTP/API contracts; relational data; transactions; design and test strategy; distributed integration; production operations | G4 |
| FDE solution design | 10 | Discovery, solution selection, system design, and design review | G5 |
| AI engineering and governance | 11–15 | LLM API; context and retrieval; agents and MCP; evaluation; security and governance | G8 |
| Delivery and evidence | 16–17 | Rollout, adoption, outcome measurement, capstone, and defense | G9 |

This order deliberately puts HTTP, data correctness, testing, and failure handling before complex agent architectures. AI is a later capability layer built on software engineering foundations, not a substitute for them. The roadmap does not require learning every language or framework. Practise backend and API-integration work in TypeScript/Node.js (Phases 2–10): TypeScript to Depth 3; Node.js at the depth Phase 3 defines. NestJS is platform literacy at Depth 1–2 (enough to read Twenty's host), not a separate track (P7.8). Next.js is studied at Depth 1–2 for server/client boundaries, data fetching, caching, and rendering in the existing website (P7.7); React code is reviewed inside that boundary. Use Python for the AI-engineering labs from P11.2. Language-track consequences follow rule 10 (projects the capstone does not need stay code-review contexts).

## 3. Lesson design and completion criteria

Every lesson follows this record shape:

- **ID and objective:** one capability that can be demonstrated.
- **Priority:** must-have, important, or useful — a planning weight, not permission to skip prerequisites (see Priority below).
- **Depends on (hard prerequisite):** required lesson IDs that must appear **earlier in this file's order**, not just earlier topics. `scripts/journey_inventory.py` runs the forward-dependency and cycle checks on these edges only.
- **Coupled with:** a non-blocking relationship built in one phase and verified (or completed) in a later one. May point forward; it must reference an existing unit ID but the cycle and file-order checks ignore it. Used so that an earlier unit does not silently re-teach a later phase's content.
- **Source:** specific project source IDs and/or official documentation to open.
- **Lesson:** scenario → concept → mechanism → failure modes → production implications.
- **Practice:** one tangible task, preferably on the evolving capstone or a deliberately small lab.
- **Exit evidence:** one primary proof artifact (checkable sub-items inside it are allowed).
- **Retrieval:** defined once in the Retrieval table below — a named later unit whose scenario re-tests this one. No per-unit Retrieval field.
- **Unit type:** lessons (about 45–90 minutes) vs **implementation unit (multi-session)** — oversized units carry this label explicitly instead of being silently long.

### Depth scale

| Depth | What it means | Example evidence |
|---|---|---|
| 0 — Recognize | Identify a concept when described | Correct classification with explanation |
| 1 — Explain | Describe why it exists and its limits | Clear explanation plus one failure mode |
| 2 — Use | Apply it in a guided, bounded task | Working implementation with basic tests |
| 3 — Engineer | Implement, debug, test, and handle failure cases | Tests, error paths, reproducible diagnosis |
| 4 — Design | Compare alternatives, consistency, security, operations, and cost | ADR plus failure analysis |
| 5 — Deep internals | Explain implementation details and edge cases | Only where required by project scope |

**Default standard:** Depth 2–3 for routine implementation lessons; Depth 3–4 for data correctness, integrations, evaluation, security, and production decisions. Depth 5 is selective, not a universal requirement.

### Priority

Each unit carries one of three priorities, keeping the priority vocabulary of the pre-rewrite journey map so the readiness check in `AGENTS.md` §4 has the metadata it names:

- **must-have** — the unit sits on the capstone's critical path: it is a dependency hub (seven or more units depend on it), it closes a gap listed in `EVIDENCE.md`, it produces the G0 problem brief/baseline, the provider contract sheet, the regression gate, or the threat model, or it is a Phase 17 capstone unit (selection, build, evidence pack, or defense).
- **important** — expected on the standard path: later units build on it or it grounds a phase gate.
- **useful** — valuable depth: compress or defer when diagnostics, the capstone, or a supporting branch show the capability is already present or not yet needed.

The old **awareness** tier has no units: every unit here carries a proof artifact, so deferral happens through the supporting branches or the project's needs, not by tagging a unit away.

### Agent review record

Used wherever a proof names an *agent review record* (rule 10). It is a short Markdown note kept with the change, with five fields:

1. **Delegation brief:** the problem, requirements, constraints, acceptance criteria, and the architecture decisions the agent must respect, written before delegating.
2. **Diff review:** the files changed, the dependencies and side effects found, and the most important changes explained in the learner's own words.
3. **Independent verification:** at least one test, query, or runtime check designed from the requirements rather than copied from the agent's own tests, plus the assumptions that remain untested.
4. **Observed evidence:** logs, traces, measurements, or failure-injection results that were actually seen.
5. **Decision:** accept, reject, or redirect, with the evidence that justifies it.

A passing generated test suite is an input to this record, never the verdict. The record is practice evidence only; it is not production experience (rule 10) and does not enter `EVIDENCE.md` as an achievement until the artifact exists.

# Phase 1 — Engineering workbench and feedback loop

**Goal:** Work reproducibly in a repository and diagnose behavior instead of guessing. **Gate G1 (closes after Phase 3):** a small project that can be run, tested, debugged, and reviewed from a clean checkout, with validated data and async contracts and runtime evidence.

- **P1.1 — Terminal, paths, processes, environment variables** — **Priority:** important. Depends on: P0.2. Navigate files; run commands; inspect exit codes, processes, and environment. **Proof:** documented run commands and diagnosis of a deliberately broken setup. Source: F1, F3.
- **P1.2 — Git fundamentals and history** — **Priority:** must-have. Depends on: P1.1. Working tree, staging, commits, branches, diffs, merge conflicts, ignore rules, remote repository. **Proof:** clean commit history and a resolved practice conflict. Source: F1.
- **P1.3 — Read an unfamiliar codebase** — **Priority:** must-have. Depends on: P1.1–P1.2. Trace entry points, configuration, module boundaries, data flow, and tests before changing code. **Proof:** a short architecture note with links to the actual files, marking each claim as verified in code or inferred; for an agent-generated codebase, state which parts could and could not be explained. Source: S40.
- **P1.4 — Debugging from evidence** — **Priority:** important. Depends on: P1.1–P1.3. Reproduce, reduce, inspect, hypothesize, test, and confirm a cause. **Proof:** a small bug report with reproduction steps, observations, cause, fix, and regression test; when an agent proposes the fix, confirm the cause by reproduction before accepting the patch. Source: F3 (runtime diagnostics).
- **P1.5 — Testing and feedback loop** — **Priority:** important. Depends on: P1.2–P1.4. Learn assertions, test setup/teardown, deterministic tests, failure output, and basic test boundaries. **Proof:** tests that fail before the fix and pass after it, including at least one test written from the stated requirement before reading the implementation. Sources: F3, F8, S41.

# Phase 2 — AI-engineering implementation bridge

**Goal:** Bridge existing C++/OOP/DSA experience into the languages, runtimes, and data contracts used by production services and AI products. This is diagnostic and just-in-time, not beginner programming. The language/stack split is stated once in section 2. The external-service boundaries opened here — request/response contracts, adapters, test seams — are the same boundaries the capstone hardens in Phase 4 and Phase 8.

- **P2.1 — Choose the implementation language for the capstone** — **Priority:** important. Depends on: P1.3, P1.5. Backend and API-integration practice uses TypeScript/Node.js; Python is introduced at P11.2 for AI-engineering labs only. **Proof:** an ADR (context, options, decision, consequences, what would make this choice wrong) recording the stack split, and one minimal HTTP call to a stub provider in TypeScript. Sources: F2, F3, F13, F14.
- **P2.2 — Data contracts and runtime validation at trust boundaries** — Implementation unit (multi-session). **Priority:** must-have. Depends on: P2.1, P1.5. JSON, schemas, serialization, missing/null/unknown fields, and the decision of where validation is enforced: at each point where data enters (HTTP requests, configuration, stored records, external-service and model-provider responses), not deep inside domain logic. The failure this addresses: a field the type system assumes exists is absent at runtime, or an external payload reaches domain logic unvalidated — including payloads a static type system accepts. Model-provider responses are one worked example, not the scope; later units reuse this discipline — model-output validation (revisited in P11.3), webhook payloads (revisited in P8.4), drift checks (revisited in P4.8a) — so do not re-teach it. **Owned-system lab:** compare opran's `packages/shared/src/validation.ts` signup/login schemas with the client forms that import them (`website/src/app/login/LoginClient.tsx`, `website/src/app/signup/SignupClient.tsx`) and the shared test; determine whether the server enforces the same contract, and state what the schema does not guarantee. **Proof:** reject malformed external payloads with actionable errors before domain logic, demonstrated with a table of valid/invalid fixtures, one of them a provider-style response and one a payload a static typechecker accepts; state which entry point each fixture covers. Sources: F2, F5, S4, S21.
- **P2.3 — Async I/O contract: concurrency, cancellation, and timeouts** — **Priority:** must-have. Depends on: P2.1–P2.2. Use existing programming knowledge over provider calls, retrieval, tools, queues, and bounded parallelism. This unit defines the async contract — which operations may run forever, which must be cancellable, how many may run at once. Node-runtime evidence (event-loop delay, resource leaks, bounded shutdown) is proven by P3.6, not here; do not re-teach it. **Owned-system lab:** trace opran's `website/src/components/demo/RideInputPanel.tsx` AbortController path (ADR-004) and write the cancellation/timeout contract it actually implements; mark any intended behavior the file does not show as unverified. **Proof:** a written cancellation/timeout contract for one async call plus a bounded-parallelism implementation that honors it deterministically. Sources: F3, F13.
- **P2.4 — External-service adapters and SDK ergonomics (AI SDKs as the worked example)** — Implementation unit (multi-session). **Priority:** important. Depends on: P2.1–P2.3. Read an SDK's types and versioning policy, inspect request/response objects, pin dependencies, and isolate third-party clients behind your own typed adapter so provider churn, retries, and SDK type gaps cannot leak into domain code. The failure this addresses: SDK types treated as runtime guarantees, or an SDK upgrade silently changing behavior under you. **Proof:** a small adapter with typed inputs, safe configuration, a pinned dependency, and tests against recorded or stub responses — the shared stub provider built in Phase 4 extends these fixtures. Sources: F3, F5, S4, S21.
- **P2.5 — Test seams for external services (provider mocks without self-deception)** — **Priority:** important. Depends on: P2.2–P2.4. Implementation unit (multi-session). Mock external-service boundaries to test contract and error paths deterministically, without pretending mocks prove real-provider or model quality; decide what the mock must reproduce (status codes, malformed payloads, latency), what it must not claim (behavior nobody has verified against the real provider), and preserve recorded fixtures for later real evaluation. The failure this addresses: a green suite that only proves the mock and the implementation share the same wrong assumption. **Proof:** unit tests for contract/error paths plus a clearly separated live smoke test run with a personal or sandbox credential, isolated from the test suite; list the assumptions the mock encodes and which later check (live test, P4.8a drift test, P14.1 evaluation) would falsify each. Sources: F8, S15; S22 (deprecated — see the S22 note in §7).

**Goal:** Build production service code in TypeScript/Node.js (stack split: section 2).

- **P3.1 — Types and compiler/runtime feedback** — **Priority:** important. Depends on: P2.1–P2.5. Use the chosen language's type system, static checks, and diagnostics where available. **Proof:** turn the Phase 2 payload normalizer into typed, checked code. Sources: F3, F5.
- **P3.2 — Valid and invalid data states** — **Priority:** important. Depends on: P3.1, P2.4, P2.2. Model optional data and event variants explicitly. **Proof:** process multiple event types without unsafe assumptions. Sources: F3, F5.
- **P3.3 — merged into P2.2.** Tombstone: runtime validation at trust boundaries is taught once, in P2.2 (which now covers the runtime-vs-static distinction its fixture table demonstrates). Dependents re-pointed to P2.2.
- **P3.4 — Process, packages, and scripts** — **Priority:** must-have. Depends on: P1.1–P1.2, P2.5, P3.1. Process lifecycle, dependency lockfiles, package scripts, and reproducible startup. Configuration files, config validation, and secret boundaries are P3.7's unit; do not re-teach them here. **Proof:** bootstrap a reproducible service in TypeScript/Node.js using P3.7's configuration and secret conventions. - **P3.5 — Non-blocking I/O and blocking work** — **Priority:** must-have. Depends on: P2.3, P3.4. Sources: F3, S28 ch. 4 (read: concurrency models and the event loop); S19 ch. 9 [TOC]. The leak and shutdown evidence is the learner's own runtime evidence, not a book claim.
- **P3.7 — Logging, configuration, and secret hygiene** — **Priority:** important. Depends on: P3.4, P3.6. The single treatment of configuration, secrets, and diagnostics hygiene in Phases 1–10: structured logs, config validation, secret injection and storage, and redaction in logs. **Proof:** logs support diagnosis without exposing credentials. Sources: F3, F11.

# Phase 4 — Internet, HTTP, and API contracts

**Goal:** Understand the contract across a network boundary before designing integrations.

- **P4.1 — Network request mental model** — **Priority:** important. Depends on: P2.2, P3.4. Client/server, DNS at a conceptual level, connection, TLS purpose, and network failure boundaries. **Proof:** trace a request from client to server and name where failures may occur. Source: F4.
- **P4.2 — HTTP request and response anatomy** — **Priority:** important. Depends on: P4.1. Methods, paths, headers, body, status codes, content types, and caching semantics. **Proof:** inspect several real requests/responses and explain their contracts. Source: F4.
- **P4.3 — Resource design and REST-style APIs** — **Priority:** important. Depends on: P4.2, P3.2, P2.2. Resource identity, methods, representation, validation, pagination, and versioning. Boundary: this contract is the single source of truth that the service unit implements (revisited in P4.7a) and the drift fixtures re-test (re-tested by P4.7b); the status/error taxonomy is owned here, not re-decided per endpoint. **Proof:** design an API contract for the capstone before implementation, including an error model (status mapping, stable machine-readable codes, no internal detail leaked, and no 403/404 distinction that lets a caller enumerate resources). Sources: F4, S39 (§2.5, REC-API-23); RFC 9457 and OpenAPI 3.1 (to verify, see `RESOURCES.md`).
- **P4.4 — Authentication and authorization basics** — **Priority:** must-have. Depends on: P4.2–P4.3, P3.7. API keys, bearer tokens, OAuth concepts, scopes, ownership checks, and secret hygiene. Issuing your own sessions/tokens and a role matrix for the capstone API is P4.9 — this unit consumes and verifies credentials, P4.9 issues them. **Owned-system lab:** trace one Eagles authorization path from a route handler through `eagles-wrms-app/src/logic-functions/caller-role.helper.ts`, and state what happens on a null role and on a database throw; compare the observed behavior with AD-30's fail-closed rule. **Proof:** test allowed and denied requests, including one cross-user object-access test written from the requirement rather than from the generated handler; state the difference between authentication and authorization. Sources: F4, F11, S39 (§2.2–2.3, REC-API-11–12).
- **P4.5 — HTTP failure semantics and the client retry decision** — **Priority:** must-have. Depends on: P2.3, P4.2. Timeouts, 4xx/5xx categories, 429, `Retry-After`, and why not every error should be retried. This unit decides, per call, which outcomes are retryable from the client side; budgets, backoff curves, jitter, and retry storms are taught once in P8.3. **Owned-system lab:** classify opran's demo retry control (`website/src/app/demo/DemoClient.tsx`, ADR-010) as user-initiated or automatic, and state which failures it does and does not recover. **Proof:** write a client policy table for retryable and permanent outcomes. Sources: F4, S25.
- **P4.6 — API data contracts and schema evolution** — **Priority:** must-have. Depends on: P2.2, P4.3. Validation, unknown fields, additive/breaking changes, compatibility, and idempotent client behavior. **Proof:** test old and new payload versions; name, from the requirement, which consumer breaks on a breaking change before writing the compatibility test. Sources: F4, F11.
- **P4.7a — Build and test a small HTTP service/client** — **Priority:** must-have. Depends on: P3.1, P3.2, P3.4–P3.7, P4.1–P4.6. Implement one endpoint, one client, validation, errors, and tests against P4.3's contract. **Proof:** reproducible service and contract tests, built from a written delegation brief with an agent review record (§3) for each agent-written part. Sources: F3, F4, F8, S40.
- **P4.7b — Fault-injection stub provider (the shared harness)** — **Priority:** must-have. Depends on: P4.7a. Build one stub provider with switchable fault modes that Phases 8–17 reuse rather than rebuild: latency, 5xx, 429 with `Retry-After`, timeout-after-commit, duplicate and out-of-order delivery, invalid signature or replay, expired or revoked token, schema drift, outage. **Proof:** the harness, with each fault mode triggerable by a named switch and an executable fixture per mode; before any harness code is written, list the observable symptom each fault mode must produce. Sources: F3, F4, F8, S37, S40.
- **P4.7 — split into P4.7a (service/client) and P4.7b (fault harness).** Tombstone: dependents re-pointed; the stub fault modes now live in P4.7b.
- **P4.8a — Third-party API onboarding: provider contract sheet and drift tests** — **Priority:** must-have. Depends on: P4.4–P4.6, P4.7a–P4.7b. Document what the provider guarantees instead of assuming it: authentication model, scopes and permissions, quotas and rate limits, pagination, idempotency support, webhook delivery, ordering, and replay behavior, schema and versioning policy, and sandbox-versus-production differences. Scope the sheet to the endpoints the capstone actually calls; the first pass covers only those, and other provider claims stay questions. **Proof:** a contract sheet for one real or sandbox API with every claim tagged documented (canonical URL and section), observed (fixture or test), or unknown; contract tests plus a drift test against the P4.7b harness that fails on a changed fixture; agent-written client code checked against the sheet, with each mismatch recorded as a finding. Sources: F4, F11, S19 ch. 5 [TOC], S27 ch. 5 [TOC], S37, S39 (§2.3, REC-API-11, REC-API-15–16); RFC 9700 and OpenAPI 3.1 (to verify, see `RESOURCES.md`).
- **P4.8b — Credential lifecycle and provider failure matrix** — **Priority:** must-have. Depends on: P4.8a. Token acquisition, expiry, refresh, revocation, and secret rotation where the provider's documented contract calls for them. **Proof:** a credential-lifecycle test, with the provider's documented expiry and revocation behavior stated in one line before the test is written, including concurrent requests at token expiry where the provider issues expiring tokens; a failure matrix for provider-side faults using the section 3 failure-matrix template with a provider-specific delta (no new format). Sources: F4, F11, S19 ch. 5 [TOC], S27 ch. 5 [TOC], S39 (§2.3, REC-API-11, REC-API-15–16); RFC 9700 (to verify, see `RESOURCES.md`).
- **P4.8 — split into P4.8a (contract sheet + drift tests) and P4.8b (credential lifecycle + failure matrix).** Tombstone: dependents (P8.4, P8.7) re-pointed to P4.8a.
- **P4.9 — Issue and rotate your own auth: sessions, tokens, and role matrix** — **Priority:** must-have. Depends on: P4.4, P4.8a–P4.8b, P4.7a. Boundary: P4.4 consumes and verifies credentials; this unit issues and revokes them for the capstone API — issuance, expiry, rotation, revocation, and a role matrix for allowed/denied actions. The provider-side lifecycle was P4.8b; this unit owns your service's. The lesson teaches the signing, expiry, and rotation mechanics before the role matrix is built. **Proof:** an issued credential expires on schedule, is rejected after revocation, and the role matrix denies one cross-role action (P4.4's cross-user test pattern reused against issuance). Sources: F4, F11, S39 (§2.2–2.3, REC-API-11–12).

# Phase 5 — Relational data and SQL

**Goal:** Model persisted facts correctly before relying on AI or distributed behavior.

## 5. Suggested capstone shape

Start with a narrow workflow such as an internal operations request or support-triage process using synthetic or approved data. Do not start by building a general-purpose autonomous assistant.

1. **Deterministic baseline:** request intake, validation, persisted state, audit history, and a clear human workflow.
2. **Integration:** one external API or webhook with authentication, deduplication, bounded retries, and reconciliation.
3. **AI feature only if justified:** for example classification, extraction, or grounded knowledge lookup. Compare its results with a deterministic baseline.
4. **Evaluation and safety:** labelled test set, edge/adversarial cases, regression checks, permission controls, and human approval for consequential actions.
5. **Production shape:** observability, timeouts/budgets, deployment, rollback, small pilot, runbook, and honest impact measurement.

The capstone must remain small enough to finish and test. Add a component only when a requirement or observed failure justifies it. Build the backend and integration parts in TypeScript/Node.js with PostgreSQL; use Python for the AI feature where the AI lessons require it, behind a stable contract. Delegate each slice from a written brief and close it with an agent review record.
