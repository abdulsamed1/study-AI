# FDE Journey Map — Deep Engineering Roadmap

**Purpose:** Build durable engineering capability for taking a real business problem from discovery to a reliable, evaluated, secure, deployed AI-enabled system. This is a long-form learning journey.

**Mission alignment:** FDE = problem discovery → choose the right solution (including non-AI) → build → evaluate → secure → deploy → integrate into work → measure impact → hand over. The target is demonstrable engineering judgment, not completion of a syllabus.

Phases 0-1 were merged into Phase 2; the old-to-new mapping is in §8.

---

## 1. Rules for this journey

1. **Follow dependencies, not enthusiasm.** Each lesson lists its prerequisite lesson IDs. A lesson is ready only when its prerequisite's exit evidence exists.
2. **Teach one lesson unit at a time.** Progression is competency-based and self-paced: a unit is complete when its proof artifact meets the exit criteria, not when a clock expires. Standard units cover one focused capability; implementation units span larger multi-part builds.
3. **Teaching mechanics live in `AGENTS.md`.** The lesson loop (teach → model → practice → review → retrieve later), evidence/synthesis separation, spacing, records, and honest phrasing of experience follow `AGENTS.md` §3, §5, §8, §11, and §13 — this map does not restate them.
4. **No progress by attendance.** Mark a lesson complete only when its proof artifact or practical performance meets the exit criteria.
5. **Respect established experience.** The user already has C++, OOP, and DSA experience. Do not teach beginner programming, object-oriented programming, or generic algorithm lessons. Use diagnostics to identify only the language, runtime, API, data, or AI-engineering gaps needed for the capstone.
6. **One evolving capstone.** Build a small, deterministic business workflow first; add persistence and integrations; introduce AI only when the use case justifies it; then evaluate, secure, deploy, pilot, and document it. Keep scope narrow.
7. **Source discipline.** `RESOURCES.md` remains the canonical project source register. Existing `S#` tags refer to it. The `F#` references below are official starting points checked on 2026-10-09; re-open the relevant page and record the exact section/version before teaching. Current API/model/security behavior must be verified at lesson time. A chapter tagged `[TOC]` was identified from a book's table of contents only and has not been read; keep the tag until the exact passage is read in an available tool and recorded in the `RESOURCES.md` reading-status table. A read that covered only the supporting sections is tagged `(read: <sections>)`; a chapter read in full is tagged `(read)`.
8. **This is a dependency graph represented as a mostly linear path.** Some concepts can be revisited later. Do not force advanced internals when the mission does not need them.
9. **Stay on the FDE/AI-engineer track.** Out of scope: training or building foundation models, ML research, and math beyond the applied evaluation protocol in P14.3 (see `MISSION.md`). Teach models and providers as engineering constraints — guarantees, cost, latency, failure modes — never as model internals.
10. **Human-in-the-loop engineering.** The learner directs coding agents and stays accountable for the result; an agent's output is an input to review, never proof by itself. Before delegating, write the problem, requirements, constraints, acceptance criteria, and architecture decisions. After the agent changes the code, review the diff, its dependencies and side effects, and the tests it wrote; design at least one verification independently of the agent's own tests; observe the real behavior across API, application logic, database, and user-facing workflow; diagnose failures from logs, traces, measurements, and failure injection; then record accept, reject, or redirect with evidence (the agent review record in section 3). Passing tests are necessary, not sufficient (S40, S41). A lab proves a lab skill: label simulated data and pilots honestly, and phrase missing experience with the honesty rules in `AGENTS.md` §11. Projects in languages the capstone does not need (for example Rust) remain code-review contexts, not additional language tracks.

11. **Hand-writing versus review.** Hand-write first when the skill is the learning target: a new concept the learner has not yet demonstrated unaided, correctness-critical work (transactions, concurrency, authorization, idempotency), and debugging. Delegate repeated mechanics and work in skills the learner has already demonstrated unaided; the delegation brief, diff review, independent verification, and accept/reject/redirect decision stay exactly as in rule 10. When an agent is used to learn, use it to build comprehension as well as output — ask it for explanations and conceptual questions, not only for code (S44). Delegating never transfers accountability: the learner still explains, modifies, or fixes the result without the agent, and owns it in the evidence pack (P17.3–P17.4) (S43).

## 3. Lesson design and completion criteria

Every lesson follows this record shape:

- **ID and objective:** one capability that can be demonstrated.
- **Priority:** must-have, important, or useful — a planning weight, not permission to skip prerequisites (see Priority below).
- **Depends on (hard prerequisite):** required lesson IDs that must appear **earlier in this file's order**, not just earlier topics. The forward-dependency and cycle checks are run with an ad-hoc script at edit time; no inventory script is currently committed (the previous script was removed in `ee744ff`).
- **Coupled with:** a non-blocking relationship built in one phase and verified (or completed) in a later one. May point forward; it must reference an existing unit ID but the cycle and file-order checks ignore it. Used so that an earlier unit does not silently re-teach a later phase's content.
- **Source:** specific project source IDs and/or official documentation to open.
- **Lesson:** scenario → concept → mechanism → failure modes → production implications. For a hands-on reliability mechanism, the incident-grounded cycle in `AGENTS.md` §8 replaces the scenario-first opening while keeping the same lesson parts (mapping: `TEACHING-PROTOCOLS.md` P§3).
- **Practice:** one tangible task, preferably on the evolving capstone or a deliberately small lab.
- **Exit evidence:** one primary proof artifact (checkable sub-items inside it are allowed).
- **Retrieval:** defined once in the Retrieval table below — a named later unit whose scenario re-tests this one. No per-unit Retrieval field.
- **Unit type:** standard lesson units (focused capability and proof) vs **implementation unit (multi-session)** (larger architectural build, multi-part design, or lab).

### Depth scale

| Depth | What it means | Example evidence |
|---|---|---|
| 0 — Recognize | Identify a concept when described | Correct classification with explanation |
| 1 — Explain | Describe why it exists and its limits | Clear explanation plus one failure mode |
| 2 — Use | Apply it in a guided, bounded task | Working implementation with basic tests |
| 3 — Engineer | Implement, debug, test, and handle failure cases | Tests, error paths, reproducible diagnosis |
| 4 — Design | Compare alternatives, consistency, security, operations, and cost | ADR plus failure analysis |
| 5 — Deep internals | Explain implementation details and edge cases | Only where required by project scope |

**Default standard:** Depth 2–3 for routine implementation lessons; Depth 3–4 for data correctness, integrations, evaluation, security, and production decisions. Depth 5 is selective, not a universal requirement.

### Priority

Each unit carries one of three priorities, keeping the priority vocabulary of the pre-rewrite journey map so the readiness check in `AGENTS.md` §4 has the metadata it names:

- **must-have** — the unit sits on the capstone's critical path: it is a dependency hub (seven or more units depend on it), it closes a gap listed in `EVIDENCE.md`, it produces the G1 Problem Card/short baseline, the provider contract sheet, the regression gate, or the threat model, or it is a Phase 17 capstone unit (selection, build, evidence pack, or defense).
- **important** — expected on the standard path: later units build on it or it grounds a phase gate.
- **useful** — valuable depth: compress or defer when diagnostics, the capstone, or a supporting branch show the capability is already present or not yet needed.

The old **awareness** tier has no units: every unit here carries a proof artifact, so deferral happens through the supporting branches or the project's needs, not by tagging a unit away.

### Agent review record

Used wherever a proof names an *agent review record* (rule 10). It is a short Markdown note kept with the change, with five fields:

1. **Delegation brief:** the problem, requirements, constraints, acceptance criteria, and the architecture decisions the agent must respect, written before delegating.
2. **Diff review:** the files changed, the dependencies and side effects found, and the most important changes explained in the learner's own words.
3. **Independent verification:** at least one test, query, or runtime check designed from the requirements rather than copied from the agent's own tests, plus the assumptions that remain untested.
4. **Observed evidence:** logs, traces, measurements, or failure-injection results that were actually seen.
5. **Decision:** accept, reject, or redirect, with the evidence that justifies it.

A passing generated test suite is an input to this record, never the verdict. The record is practice evidence only; it is not production experience (rule 10) and does not enter `EVIDENCE.md` as an achievement until the artifact exists.

### AI-provider dependency thread (Phases 2–9)

A model provider is an external service with a contract, a failure surface, a latency profile, and a price. The thread below makes that context recur from the first service onward without moving any advanced mechanism out of its owning unit. Each row is a **bridge exercise inside the primary unit named**, run against the P2.1 stub provider (extended by P4.7b) or a recorded fixture; the other units in a row are ownership boundaries, not additional bridges. No row is a new unit, a new gate, or evidence that a later unit is complete.

| Phase | Bridge exercise: fault scenario | Owning unit and capability | Boundary |
|---|---|---|---|
| 2 | The stub provider returns a provider-shaped 5xx error body; later, a malformed or unexpected payload | P2.1 fails visibly and proves it with a regression test; P2.2 owns trust-boundary validation and runtime rejection | P2.1 does not validate schemas or classify retries; P2.2 does not decide retry policy |
| 3 | A slow provider call holds execution resources past the caller's deadline | P3.6 owns timeout, cancellation, and bounded cleanup, against the async contract defined in P2.3 | A timeout is a failure, not a fix; retries stay out |
| 4 | A provider HTTP outcome violates the expected contract | P4.5 owns retryable-versus-permanent classification; P4.8a owns the provider contract sheet | Budgets, backoff curves, and jitter stay in P8.3 |
| 5 | Validated provider output must become persisted business state | P5.3 and P5.6 own constraints, integrity, and parameterized access | No model semantics enter the schema |
| 6 | A repeated or overlapping request risks a duplicate business effect | P6.5 owns duplicate and stale event transitions; P8.2 owns operation keys and retention | P6 does not build a queue or a delivery guarantee |
| 7 | A green suite passes while a meaningful behavioral defect survives | P7.2–P7.3 own independent regression tests and honest test doubles | A mock passing is not evidence about the provider |
| 8 | Rate limiting, transient failure, repeated delivery, or partial completion | P8.3 owns bounded retries and backoff; P8.4 webhook contracts; P8.5 durable workers | P8 does not re-teach the HTTP categories from P4.5 |
| 9 | Provider latency, request volume, or cost rises while the system degrades | P9.3 tracing, P9.4 SLI, P9.6 capacity diagnosis | Cost stays an estimate until a real provider bill or measured usage exists |

**Ownership rules.**

1. The bridge changes how a unit is practised, not what it proves. The unit's own proof artifact and exit criteria stand.
2. A bridge never marks a later unit complete, and no later unit may depend on a bridge.
3. A later unit may re-use the bridge's fixture, but it must re-derive its own contract, measurement, or test from its own source.
4. The early model-exposure checkpoint (§10) is the only live-provider step before Phase 11; every other bridge is stub-based and labelled simulated.

# Phase 2 — AI-engineering implementation bridge

**Goal:** Work reproducibly in a repository, diagnose behavior instead of guessing, and bridge existing C++/OOP/DSA experience into the runtimes and data contracts used by production services and AI products. Start from a running slice, not a planning set: P2.1 produces one HTTP call, one seeded provider failure, and one regression test before any broader artifact. **Gate G1 (closes after Phase 3):** a small project that can be run, tested, debugged, and reviewed from a clean checkout, with a five-line Problem Card, a short evidence-based baseline, validated external data, an async contract with runtime evidence, and an HTTP contract and auth boundary.

**Handbook reading path (S69 [TOC]):** Ch. 36 §36.29 (responsible use of coding assistants); Ch. 37 §§37.2, 37.4–37.6, 37.13–37.15 (Python baseline, HTTP app structure, validation/error contracts, tests, project layout, production run). Keep P2.1 stub-only and preserve the existing requirement-first regression proof.

This is diagnostic and just-in-time, not beginner programming. The external-service boundaries opened here — request/response contracts, adapters, test seams — are the same boundaries the capstone hardens in Phase 4 and Phase 8; P2.1 opens the first one as a stub provider. Python implementation claims for P2.1–P2.5 are grounded in verified sources F15–F18 and `TEACHING-PROTOCOLS.md` P§6. F2/F3/F5 support only conditional code-reading of an existing system when a named owned-system task requires it; they are not part of the default Python implementation curriculum.

- **P2.1 — Minimum reliable service: one stub-provider call, one seeded provider failure, one regression test** — **Priority:** must-have. Depends on: none. Python is fixed as the capstone language by section 2, so no language decision is re-opened here. Bootstrap the toolchain exactly as `TEACHING-PROTOCOLS.md` P§6 specifies — one virtual environment and pinned dependencies — plus a clean Git repository. Build the smallest service that calls a local stub provider over HTTP, maps the success response to a typed object, and returns a deterministic result. Then add **one** named failure switch to the stub — for example a 503 with a provider-shaped error body — reproduce it with a deterministic fixture, write the regression test first, watch it fail against the naive implementation, correct the smallest defect, and watch it pass. Keep every other mechanism out: malformed payloads and schema validation are P2.2, timeouts and cancellation P2.3/P3.6, status classification P4.5, duplicate effects P6.5/P8.2, retry budgets P8.3, observability P9.3. **AI-dependency bridge:** this is the first provider-shaped boundary; the stub stands in for a model provider, and the seeded fault is an availability/transport fault, not a schema fault. **Proof (one primary artifact — the service repository, with checkable sub-items):** a clean checkout starts from the README run commands and the P§6 version checks are recorded in the run log; one automated test fails under the seeded fault and passes after the correction, with both runs recorded; `docs/problem-card.md` holds exactly five labelled lines — intended user, workflow, current pain or hypothesis, initial success signal, most important constraint — with every unknown marked as a hypothesis rather than a fact; and `EVIDENCE.md` holds the short baseline (one line per assessed dimension with the evidence that supports it, unassessed dimensions named as unassessed). No language ADR (the decision is already made), no comprehensive brief, no delivery-loop diagram, no separate CLI document, no merge-conflict exercise, and no environment-diagnosis exercise in this unit. Sources: F1, F15, F16, F17, F18; `AGENTS.md` §6.
- **P2.2 — Data contracts, trust boundaries, and runtime failure debugging** — Implementation unit (multi-session). **Priority:** must-have. Depends on: P2.1. JSON, schemas, serialization, missing/null/unknown fields, and enforcing validation at every entry point where data enters (HTTP requests, configuration, stored records, external-service and model-provider responses), not deep inside domain logic. Establish requirement-first test discipline: write assertions from the contract specification before writing the parsing implementation, observing tests fail (red) before they pass (green). Practice evidence-based debugging: reproduce unexpected or poisoned payload failures with a test harness, inspect traces, hypothesize, fix the validation boundary, and verify the regression test. **Conditional owned-system lab:** when verifying the existing opran codebase is relevant to the current task, compare `packages/shared/src/validation.ts` signup/login schemas with the client forms that import them (`website/src/app/login/LoginClient.tsx`, `website/src/app/signup/SignupClient.tsx`) and the shared test; determine whether the server enforces the same contract, and state what the schema does not guarantee. Skip this code-reading branch when it does not serve the selected task. **Proof:** reject malformed external payloads with actionable errors before domain logic, demonstrated with a table of valid/invalid fixtures, one of them a malformed-response mode added to the P2.1 stub and one a payload a static typechecker accepts; state which entry point each fixture covers; a bug report for an injected malformed payload with reproduction steps, cause, fix, and regression test; and test suite execution output showing requirement-first assertions. **AI-dependency bridge:** the malformed provider response is the first untrusted external payload; the schema is written from the provider contract, not from the fixture. Sources: F2, F3, F5, F8, F17, S4, S21, S40, S41, S44.
- **P2.3 — Async I/O contract: concurrency, cancellation, and timeouts** — **Priority:** must-have. Depends on: P2.1–P2.2. Use existing programming knowledge over provider calls, retrieval, tools, queues, and bounded parallelism. This unit defines the async contract — which operations may run forever, which must be cancellable, how many may run at once. Runtime evidence (Python `asyncio` scheduling, resource leaks, and bounded shutdown in the capstone service) is proven by P3.6, not here; do not re-teach it. **Owned-system lab (conditional code reading):** trace opran's `website/src/components/demo/RideInputPanel.tsx` cancellation path (ADR-004) only as needed to distinguish the behavior the existing UI implements from the Python service's async contract; mark any behavior not shown in code as unverified. **Proof:** a written cancellation/timeout contract for one async call plus a bounded-parallelism implementation that honors it deterministically. Sources: F15, F18.
- **P2.4 — External-service adapters and SDK ergonomics (AI SDKs as the worked example)** — Implementation unit (multi-session). **Priority:** important. Depends on: P2.1–P2.3. Inspect the chosen Python client's request/response contract and versioning policy, pin dependencies, and isolate the provider behind a typed adapter so provider churn or SDK type gaps cannot leak into domain code. Runtime validation remains P2.2; provider behavior remains verified against the live contract or controlled fixtures, not inferred from SDK types. **Proof:** a small adapter with typed inputs, safe configuration, a pinned dependency, and tests against recorded or stub responses — the shared stub provider built in Phase 4 extends these fixtures. Sources: F15, F16, S4, S21.
- **P2.5 — Test seams for external services (provider mocks without self-deception)** — **Priority:** important. Depends on: P2.2–P2.4. Implementation unit (multi-session). Mock external-service boundaries to test contract and error paths deterministically, without pretending mocks prove real-provider or model quality; decide what the mock must reproduce (status codes, malformed payloads, latency), what it must not claim (behavior nobody has verified against the real provider), and preserve recorded fixtures for later real evaluation. The failure this addresses: a green suite that only proves the mock and the implementation share the same wrong assumption. **Proof:** unit tests for contract/error paths plus a clearly separated live smoke test run with a personal or sandbox credential, isolated from the test suite; list the assumptions the mock encodes and which later check (live test, P4.8a drift test, P14.1 evaluation) would falsify each. Sources: F18, S15.

## 5. Suggested capstone shape

Start with a narrow workflow such as an internal operations request or support-triage process using synthetic or approved data. Do not start by building a general-purpose autonomous assistant.

1. **Deterministic baseline:** request intake, validation, persisted state, audit history, and a clear human workflow (the P2.1 Problem Card is the seed, not the final brief).
2. **Integration:** one external API or webhook with authentication, deduplication, bounded retries, and reconciliation.
3. **AI feature only if justified:** for example classification, extraction, or grounded knowledge lookup. Compare its results with a deterministic baseline.
4. **Evaluation and safety:** labelled test set, edge/adversarial cases, regression checks, permission controls, and human approval for consequential actions.
5. **Production shape:** observability, timeouts/budgets, deployment, rollback, small pilot, runbook, and honest impact measurement.

The capstone must remain small enough to finish and test. Add a component only when a requirement or observed failure justifies it. Build the backend, integration, and AI parts in Python with PostgreSQL; keep the model call behind a stable contract. TypeScript/Node.js remains the reading context for opran and the Twenty/Eagles host, not a second capstone implementation. Delegate each slice from a written brief and close it with an agent review record.

**Capstone evolution flow.** The capstone system evolves organically across milestones rather than starting at the end. Each artifact belongs to the stage that can produce it honestly:
1. **Five-line Problem Card (P2.1):** the seed — intended user, workflow, current pain or hypothesis, initial success signal, most important constraint; unknowns are hypotheses, not facts.
2. **Evidence-informed discovery and selection (P10.1–P10.3):** current-state workflow map, stakeholder questions, the non-AI comparison (P10.2), and the baseline measurement plan with an owner and collection method (P10.3). P10.1 replaces the Problem Card's provisional workflow observation; it does not inherit the card as a finished brief.
3. **Early evaluation case set (P14.1):** representative, edge, and adversarial cases from the workflow and testing discipline, completed before the first model call in M3; model-specific cases are added after P11.2–P11.3.
4. **Formal system design (P10.4a–P10.4c) and design review (P10.7):** requirements and capacity, interfaces and components, the architecture decision, failure/security risk matrix, validation plan, and the go/adjust/stop decision.
5. **AI-dependency containment and rollout design (P16.1, P16.3):** degradation, fallback to deterministic rules, human escalation, and stop conditions — designed before the capstone build, not after it.
6. **Capstone selection and vertical slices (P17.1–P17.2):** confirm data/users, a measurable baseline, bounded risk, and a reason AI is appropriate; then deliver thin vertical slices with tests, contracts, migrations, failure paths, and an agent review record per slice.
7. **Real pilot, measured outcome, evidence pack, and defense (P16.4–P16.5, P17.3–P17.4):** observed pilot feedback, before/after outcome with data provenance, the consolidated pack, and the technical defense. These stay conditional on a real workflow owner and real users.

**Early model-exposure checkpoint (between M1 and M3; not a unit).** Once G1 has closed, the P2.4 adapter plus the P4.1–P4.4 HTTP foundations are demonstrated, and P14.1's first case set is complete, run one deliberate live-provider checkpoint before the formal model sequence in M3. It has three parts: (1) one real model call through the P2.4 adapter, using a provider contract opened at teach time (endpoint, auth, request and response fields, documented error codes) and a stated spend cap; (2) one controlled failure — a documented provider error or an invalid credential — handled as a typed failure, not a crash; (3) one latency measurement over a stated number of calls (n, median, p95), recorded with the date and model identifier. This is exploratory exposure, explicitly **not** P11.2: it does not satisfy P11.1–P11.4, does not change any unit's proof, priority, or dependency, does not create an evaluation claim, and is not production evidence. If credentials or a verified contract are unavailable, run the labelled alternative: the P2.4 adapter against the P2.1 stub with a recorded provider-shaped response, logged as **"simulated — no model call"**. The stub-only rehearsal does not close the checkpoint; record it as deferred with the reason, and M3's P11.2 remains the first real model call.
