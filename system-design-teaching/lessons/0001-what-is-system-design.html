Lesson 0001 of System Design from Scratch
Topic: What Is System Design & The Building Blocks
Time: ~20 min read

What Is System Design?

System design is the process of defining the architecture, components, data flow, and trade-offs of a system to satisfy requirements. It answers one question:

"Given a problem, what should we build, how should the pieces talk to each other, and why this way instead of another?"

You already do this — every time you pick a database, design an API endpoint, or decide to add a cache. System design just gives you the vocabulary and frameworks to do it deliberately.

The Five Building Blocks

Every web system, from a simple blog to WhatsApp, is made of the same five types of components:

1. Client (Frontend)

The thing the user interacts with. A browser, a mobile app, a CLI tool. It sends requests and displays responses.

In Eagles: The React frontend at app.eagles-eg.online — the dashboard, Kanban board, team tab.

2. Server (Backend/API)

Receives requests from the client, applies business logic, talks to the database, and returns responses. This is where your rules live.

In Eagles: Twenty's Node.js server — runs logic functions like assign-to-best-employee, convert-lead, evolution-message-ingestion.

3. Database

Where your data lives permanently. Think of it as the system's memory. Every lead, contract, customer, and booking is a row in PostgreSQL.

In Eagles: PostgreSQL 16 on the VPS — tables like _lead, _contract, _customer, workspaceMember.

4. Cache

A fast, temporary storage layer that sits between the server and database. If the database is a library, the cache is the book on your desk — you already looked it up once, no need to walk back.

In Eagles: Redis (running in Docker) — stores session tokens, frequently accessed data, and rate-limit counters.

5. External Services

Third-party systems your application depends on but doesn't own. Email providers, payment gateways, messaging APIs.

In Eagles: Cloudflare (DNS/TLS/protection), Evolution API (WhatsApp gateway), Meta Lead Ads API (Facebook/Instagram lead ingestion).

How Eagles Maps to These Blocks

Here's how the five blocks connect in a real production system:

User's Browser
    │
    ▼
Cloudflare (External Service — TLS, DNS, protection)
    │
    ▼
Twenty Server (Backend — Node.js, Docker Compose)
    │
    ├──► PostgreSQL 16 (Database — Pigsty-managed on host)
    ├──► Redis (Cache — Docker container)
    ├──► Evolution API (External — WhatsApp gateway)
    └──► Meta Lead Ads API (External — lead ingestion)

Every request flows: Client → Cloudflare → Server → Database/Cache/External. The server is the brain — it decides what to do with every request.

Key Vocabulary

You'll hear these terms constantly in system design interviews and architecture discussions:

Term Meaning
Throughput How many requests the system can handle per second (RPS).
Latency How long a single request takes to complete (ms).
Availability What percentage of time the system is up (99.9% = "three nines" = ~8.7 hours downtime/year).
Scalability Can the system handle more load by adding resources?
Consistency Does every user see the same data at the same time?
Idempotency If you send the same request twice, do you get the same result? Critical for retries.
Coupling How dependent are components on each other? Low coupling = changes in one place don't break others.

Eagles Uses All of These

Real Example: Lead Assignment

When a Meta Lead Ad comes in, here's what happens:

  1. External Service (Meta) sends a webhook to the Server
  2. Server runs the meta-lead-ingestion logic function (business logic)
  3. Server checks Redis (cache) for existing attributions to avoid duplicates
  4. Server writes to PostgreSQL (database) — creates the Lead, the Lead Attribution
  5. A database trigger fires: lead.created → runs assign-to-best-employee
  6. Assignment query reads all reps' open lead load from PostgreSQL
  7. Picks the rep with minimum load, writes the assignment back

Seven components. One business event. That's system design in action.

The Trade-Off Mindset

System design is never about finding the "perfect" solution. It's about understanding trade-offs:

  • Consistency vs. Availability: Can you show stale data (available) or block the user until data is fresh (consistent)?
  • Speed vs. Cost: Caching everything is fast but uses more memory. Skipping the cache is cheap but slow.
  • Simplicity vs. Scalability: A single server is simple. Adding load balancers and replicas is complex but handles more traffic.

🦅 Eagles Trade-Off: Single VPS vs. Cloud Cluster

Eagles runs on a single Hostinger VPS (2 vCPU, 8 GB RAM). Why not a Kubernetes cluster on AWS?

  • Cost: ~640 EGP/month (~$13) vs. $500+/month for cloud HA
  • Complexity: One server is simple to debug. A cluster needs DevOps expertise.
  • Risk: Single point of failure — if the VPS dies, the system is down. RTO is 2-4 hours (restore from backup to new VPS).

This is a deliberate trade-off: cost and simplicity over high availability. For a single-location workspace, this is the right call.

What You Learned

  • System design = architecture + components + data flow + trade-offs
  • Every web system has 5 building blocks: Client, Server, Database, Cache, External Services
  • Eagles is a real example of all five connected together
  • Trade-offs are the core of system design — there are no perfect solutions
  • Key vocabulary: throughput, latency, availability, scalability, consistency, idempotency, coupling
